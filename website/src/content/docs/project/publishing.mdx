This page is for maintainers cutting a release. If you just want to use BUI, [Install BUI](../../start/installation/) is what you're after.

BUI ships to three registries: **PyPI** (`blenderui`), **npm** (`@blender-ui/native` and `@blender-ui/react`) and **crates.io** (the `blenderui` crates). Each has its own version and its own steps.

## At a glance

| Registry | Package | Version lives in | How it's released |
| --- | --- | --- | --- |
| PyPI | `blenderui` | `bindings/python/bui/_version.py` | Push a `v*` tag; CI builds, tests and publishes |
| npm | `@blender-ui/native`, `@blender-ui/react` | Each package's `package.json` | `npm publish`, by hand, native first |
| crates.io | `blenderui-tailwind`, `-macros`, `-sys`, `-paint`, `-table`, `-vlist`, `blenderui`, `blenderui-imgui` | `bindings/rust/Cargo.toml` (`[workspace.package]`) | `cargo publish`, by hand, after vendoring the C sources |

## PyPI

### What a wheel contains

```text
site-packages/
  buipy.<abi>.pyd|.so     the C kit + raster engine, with Dear ImGui (blenderui.imgui) when
                           CMake builds bui_cimgui: one extension module, one kit per process
  bui/                     tksyntax/, qtsyntax.py, components/, host.py ...
  blenderui/               alias package: blenderui.X is bui.X
  blenderui-<v>.dist-info/
```

Wheels are built with [scikit-build-core](https://scikit-build-core.readthedocs.io), which drives the project's CMake. The version comes from `bindings/python/bui/_version.py`, the single source that CMake reads too. The console script `blenderui-tk app.py` is the same as `python -m bui.tksyntax app.py`.

On Windows, the extension is built with MinGW-w64 GCC (UCRT) and statically linked against the GCC runtime, so it depends only on system DLLs and Python's own. A wheel is about 0.4 MB compressed; the sdist is about 1.7 MB.

### CI

The `.github/workflows/wheels.yml` workflow has four jobs:

| Job | Does |
| --- | --- |
| `wheels` | `cibuildwheel` for Linux (manylinux x86_64, with the X11 headers installed so wheels get the native host), Windows (MinGW, x86_64) and macOS (arm64 and x86_64), for CPython 3.11 to 3.14. Each wheel is imported as a smoke test. |
| `sdist` | `python -m build --sdist` |
| `tests` | A CMake build and `ctest` (all C and Python suites) on Windows |
| `publish` | On a `v*` tag, uploads everything to PyPI with trusted publishing. A manual run with `testpypi` uploads to TestPyPI. |

### One-time setup

1. Create the `blenderui` project on PyPI and register it as a [pending trusted publisher](https://docs.pypi.org/trusted-publishers/) for this repository: workflow `wheels.yml`, environment `pypi`.
2. Do the same on TestPyPI with the environment `testpypi`.
3. In the GitHub repository settings, create the environments `pypi` and `testpypi` (optionally with required reviewers).

No API tokens are stored anywhere.

### Release checklist

<Steps>

1. **Bump the version** in `bindings/python/bui/_version.py`, following semantic versioning.

2. **Add the release to `CHANGELOG.md`.**

3. **Test locally.** `ctest --test-dir build` must pass. Optionally run the workflow by hand with `testpypi`, then:

   ```sh
   pip install -i https://test.pypi.org/simple blenderui
   ```

4. **Tag and push.** CI builds, tests and publishes.

   ```sh
   git tag v0.1.0 && git push --tags
   ```

</Steps>

### Build a wheel locally

```sh
python -m pip install build
python -m build                    # sdist + wheel in dist/
```

On Windows with MSYS2 MinGW (the tested toolchain), set `CMAKE_GENERATOR=MinGW Makefiles`, `CC=gcc` and `CXX=g++` first. Test the wheel in a clean virtual environment:

```sh
python -m venv /tmp/bui-venv
/tmp/bui-venv/bin/pip install dist/blenderui-*.whl
/tmp/bui-venv/bin/python -c "import blenderui, blenderui.tksyntax, blenderui.components; print(blenderui.__version__)"
```

## npm

The packages are published under the [`@blender-ui`](https://www.npmjs.com/org/blender-ui) organization. `@blender-ui/react` depends on `@blender-ui/native` (`^0.2.0`), so **publish the native package first** whenever it has changed.

```sh
npm login                                  # an account in the blender-ui org
cd bindings
npm install                                # link the workspace
cd node  && npm publish --access public    # @blender-ui/native (builds the addon and runtime, runs the tests)
cd ../react && npm publish --access public # @blender-ui/react (runs the tests)
```

- **`prepublishOnly`** runs the tests before uploading. For the native package it first builds the addon and `bui-runtime`, which needs Rust, CMake and a C compiler (with MinGW, put its `bin` folder on `PATH`).
- **`prepack`** copies the repository's `LICENSE` into the package.
- **Preview** with `npm pack --dry-run`, which lists what a package will contain.
- **Releasing again:** bump `version` in the package's `package.json` first; npm refuses to publish the same version twice. When the native package changes in a way React needs, raise React's `@blender-ui/native` range to match.

The addon and `bui-runtime` ship in one package per platform, the napi-rs convention: `@blender-ui/native-win32-x64`, `-linux-x64` (glibc 2.35 or later), `-darwin-arm64` and `-darwin-x64`. `@blender-ui/native` lists them as `optionalDependencies`, so npm and Bun install only the one that matches. `bindings/node/platform.js` lists the platforms. `node scripts/platforms.js` writes each package to `bindings/node/npm/<tag>/` at the main package's version. With `--main` (release CI only), it also writes the `optionalDependencies` into the main package's `package.json` just before publishing, as napi-rs's `prepublish` does, and stops if a platform is not built. The committed `package.json` has none, so the workspace lockfile never names a package that is not published yet. In `release.yml`, the `npm-native` jobs build on `ubuntu-22.04`, `macos-15` and `macos-15-intel`; the `npm` job builds the Windows files, then publishes the platform packages and then the main package. A new platform package must be published once by hand and given its trusted publisher; until then the workflow stops before `@blender-ui/native`. Publish that first one as a placeholder version, so no release number is used up by a local build: `node scripts/platforms.js --version 0.0.0-bootstrap`, then `npm publish --access public --tag bootstrap` in `npm/<tag>/`.

## crates.io

The eight crates below are on crates.io (version 0.2.0 at the time of writing), and users add them with `cargo add blenderui` (or `cargo add blenderui-imgui`). A tag push publishes them in dependency order:

| Crate | What it is | Depends on |
| --- | --- | --- |
| `blenderui-tailwind` | Tailwind v4 class compiler (std only) | Nothing |
| `blenderui-macros` | `rsx!` / `view!`, `#[component]`, `css!`, `tw!` | `blenderui-tailwind` |
| `blenderui-sys` | FFI over the C kit; builds it with CMake | Nothing (CMake at build time) |
| `blenderui-paint` | Shared painting types: geometry, colors, the `PaintSink` trait, the text cache | Nothing |
| `blenderui-table` | The data table's core (virtualization, sorting, selection) | `blenderui-paint` |
| `blenderui-vlist` | The variable-height list's core (height index, anchored scrolling, sources) | `blenderui-paint` |
| `blenderui` | The framework | The five above |
| `blenderui-imgui` | Dear ImGui on BUI | `blenderui-sys` |

A published crate can't reach files outside itself, so `blenderui-sys` must carry the C sources. Its build script looks for them in three places, in order: `BUI_SOURCE_DIR` if set, the surrounding repository, then `csrc/`, the vendored copy a downloaded crate has.

<Steps>

1. **Bump the version** in `bindings/rust/Cargo.toml` (`[workspace.package]`); the crates share one version. Then update the `version = "..."` of the path dependencies in `blenderui/Cargo.toml`, `blenderui-macros/Cargo.toml`, `blenderui-imgui/Cargo.toml`, `blenderui-table/Cargo.toml` and `blenderui-vlist/Cargo.toml`. `python tools/check_versions.py vX.Y.Z` checks all of them.

2. **Log in once** with `cargo login` and a crates.io API token.

3. **Vendor the C sources, then publish.** `cargo publish --workspace` orders the crates itself on Cargo 1.90 and newer:

   ```sh
   python bindings/rust/scripts/vendor_c.py          # copies ~7 MB into blenderui-sys/csrc/
   cd bindings/rust
   cargo package --workspace --allow-dirty           # optional: builds each packaged crate in isolation
   cargo publish --workspace --allow-dirty
   ```

   `--allow-dirty` is needed because `csrc/` is untracked. Users need CMake and a C compiler to build `blenderui-sys`. The benchmark in `bench/` is excluded from the workspace and never published.

</Steps>

## Known gaps before 1.0

- **macOS:** the native Cocoa host has been tried by hand on two Apple Silicon Macs so far. With `BUI_HOST=tk`, the wheels use the standard Tk window instead.
- **Windows wheels** are built with MinGW. MSVC builds work (the Rust crate and the CMake build use it), but aren't what's published.
- **No musllinux or 32-bit wheels** yet.
- **npm:** prebuilt for Windows x64, Linux x64 (glibc) and macOS; no musl or arm64 Linux.
