A UI that doesn't answer back is just a picture. **Events are how your code hears the user**: a click, a key, a dragged slider. Attach a listener to any element, change your state, and BUI redraws what changed.

## Your first listener

```rust title="src/main.rs"
use blenderui::prelude::*;

struct Counter { count: i32 }

impl Render for Counter {
    fn render(&mut self, _: &mut Window, cx: &mut Context<Self>) -> impl IntoElement {
        div().styled().p_4().flex().gap_2()
            .child(p().child(format!("Count: {}", self.count)))
            .child(button().child("Add one").on_click(cx.listener(|this, _: &ClickEvent, _, cx| {
                this.count += 1;
                cx.notify();
            })))
    }
}

fn main() {
    Application::new().run(|cx| {
        cx.open_window(WindowOptions::default(), |_, cx| cx.new(|_| Counter { count: 0 })).unwrap();
    });
}
```

- **`cx.listener(...)`** turns a method-like closure into a listener. You get `this` (your view, mutable), the event, the `Window` and the `Context`.
- **`cx.notify()`** asks for a re-render. Without it, your state changes but the window doesn't know.

If you use [hooks](../hooks/) instead, you don't need either: writing a signal re-renders for you.

## Every listener

Every HTML `on*` event has a listener, named the same in snake case (`onPointerDown` is `.on_pointer_down`). A listener gets the event, the `Window` and the `App`.

| Listener | Event | Bubbles |
| --- | --- | --- |
| `on_click` | `ClickEvent { down, up }`: a press and release on the element | Yes |
| `on_double_click` | `ClickEvent` (`click_count()` is 2) | Yes |
| `on_aux_click` | `ClickEvent`: a click with the middle or secondary button | Yes |
| `on_context_menu` | `ContextMenuEvent { position, modifiers }` | Yes |
| `on_mouse_down(button, f)`, `on_any_mouse_down(f)` | `MouseDownEvent { button, position, modifiers, click_count }` | Yes |
| `on_mouse_up(button, f)` | `MouseUpEvent { button, position, modifiers }` | Yes |
| `on_mouse_move` | `MouseMoveEvent { position, pressed_button, modifiers }` | Yes |
| `on_mouse_enter`, `on_mouse_leave` | `MouseMoveEvent`: this element only; moving into a child doesn't leave it | No |
| `on_mouse_over`, `on_mouse_out` | `MouseMoveEvent`: also from the children | Yes |
| `on_hover` | `bool`: `true` when the pointer enters, `false` when it leaves | No |
| `on_pointer_down`, `on_pointer_up`, `on_pointer_move` | `PointerEvent` | Yes |
| `on_pointer_enter`, `on_pointer_leave` | `PointerEvent` | No |
| `on_pointer_over`, `on_pointer_out`, `on_pointer_cancel` | `PointerEvent` | Yes |
| `on_got_pointer_capture`, `on_lost_pointer_capture` | `PointerEvent` | No |
| `on_press_drag` | `PressDragEvent { button, start, position, modifiers, direction }`: Blender's press-drag, once per press, from the first move more than 3 pixels from where the button went down | Yes |
| `on_scroll_wheel` (or `on_wheel`) | `ScrollWheelEvent { position, delta, modifiers }` | Yes |
| `on_scroll` | `ScrollEvent { offset }`: a scroll container moved | No |
| `on_key_down`, `on_key_up` | `KeyDownEvent` / `KeyUpEvent { keystroke }` | Yes, from the focused element |
| `on_focus`, `on_blur` | `FocusEvent` | No |
| `on_focus_in`, `on_focus_out` | `FocusEvent` | Yes |
| `on_change`, `on_input` | `ChangeEvent { value, checked, number }` | Yes |

Each has a `_capture` twin (`on_click_capture` …) that hears the event on the way down, before the target (see [the two passes](#the-two-passes)). Touch, drag-and-drop, clipboard, media and CSS animation events (`touchstart`, `dragstart`, `paste`, `ended`, `transitionend` …) are not there yet.

The details:

- **Positions** are in logical pixels (they don't change with display scaling).
- **`MouseButton`** is `Left`, `Right` or `Middle`.
- **`Modifiers`** has `shift`, `control` and `alt`.
- **`PointerEvent`** has `pointer_id` (the mouse is 1), `pointer_type`, `is_primary`, `button`, `buttons` (bits: 1 left, 2 right, 4 middle), `position`, `modifiers`, `pressure` and `click_count`. A press fires `pointerdown` and then `mousedown`; a move fires `pointermove` and then `mousemove`.
- **`on_context_menu` and `on_aux_click`** run when the secondary or middle button is released (a window reports the secondary button's click that way).
- **`ClickEvent::click_count()`** tells a double-click from a single one. A double click is Blender's rule: the same button pressed again within 350 ms without moving past the drag threshold.
- **`PressDragEvent::direction`** is one of eight (`DragDirection::East` … `SouthEast`), rounded to the nearest as Blender's `WM_event_drag_direction` does. The threshold is `DRAG_THRESHOLD` (3 logical pixels, Blender's `U.drag_threshold_mouse`).
- **`ScrollWheelEvent::delta`** is in lines; positive scrolls the content up (the wheel turned away from you).
- **`Keystroke`** has `key` (the key's name: `"a"`, `"Return"`, `"Left"` …), `key_char` (the typed text, if any) and `modifiers`.
- **`ChangeEvent`** carries `value` (the text), `checked` (checkboxes and radios) and `number` (numbers, ranges, and a select's index). `on_input` and `on_change` both fire when the value changes. [The three looks](../styled-and-blender-components/#form-controls) lists what each control sends.

## Listeners in rsx!

In `rsx!`, `onClick={...}` becomes `.on_click(...)`, and the same for every `on*` name: `onMouseMove`, `onKeyDown`, `onChange` … You can leave out the parameters you don't use; the macro adds `_` for the rest.

```rust
rsx! {
    <button onClick={|| println!("saved")}>"Save"</button>
    <input onInput={|e: &ChangeEvent| println!("typing: {}", e.value)} />
    <div onClick={cx.listener(|this, _: &ClickEvent, _, cx| { this.open = !this.open; cx.notify(); })} />
}
```

## The two passes

An event goes through the elements twice, as in a browser. First down from the root to the target (the **capture** pass, the `_capture` listeners), then back up (the **bubbling** pass, the ordinary listeners). `cx.stop_propagation()` ends the pass it is called in, so a capture listener can keep an event from reaching its target.

```rust
div()
    .on_click_capture(|_, _, cx| { println!("first"); cx.stop_propagation(); })  // nothing below hears the click
    .child(button().on_click(|_, _, _| println!("never")))
```

- **Clicking an element focuses it.** Key events go to the focused element, then bubble up through its ancestors. Moving focus fires `blur` and `focusout` on the old element and `focus` and `focusin` on the new one.
- **Most events bubble**: a click on a `<span>` inside a `<button>` reaches the button's `on_click` too. `on_hover`, `on_mouse_enter`, `on_mouse_leave`, `on_focus`, `on_blur` and `on_scroll` don't.
- **Enter and leave** go to each element on its own, outermost first when entering, innermost first when leaving. The order on a move is `out`, `leave`, `over`, `enter`.
- **Focus from code:** `window.focus_id("name")` focuses the element with that `.id(...)`, and `window.focused_id()` tells you which one has focus.

```rust
div().id("canvas-area")
    .on_key_down(|e: &KeyDownEvent, _, _| {
        if e.keystroke.key == "Delete" { println!("delete selection"); }
    })
```

## Dragging: pointer capture and window-wide listeners

A drag has to keep hearing the pointer after it leaves the element it started on. There are two ways.

**Pointer capture** (HTML's `setPointerCapture`): call `window.set_pointer_capture(cx)` from a listener, and the pointer and mouse events go to that element, wherever the pointer is, until the button is released (or `window.release_pointer_capture(cx)`).

```rust
div()
    .on_pointer_down(|_, window, cx| window.set_pointer_capture(cx))
    .on_pointer_move(|e: &PointerEvent, _, _| println!("at {:?}", e.position))  // also far outside it
    .on_pointer_up(|_, _, _| println!("done"))
    .on_lost_pointer_capture(|_, _, _| println!("let go"))
```

**Window-wide listeners** (gpui's `on_mouse_event`): hear every event of a kind in the window, whatever it happens on, in both passes. The listener also gets the pass:

```rust
div().on_mouse_event(|e: &MouseMoveEvent, phase, _, _| {
    if phase == DispatchPhase::Bubble { println!("the pointer is at {:?}", e.position); }
})
```

It works for `MouseDownEvent`, `MouseUpEvent`, `MouseMoveEvent`, `ScrollWheelEvent` (`on_mouse_event`) and `KeyDownEvent`, `KeyUpEvent` (`on_key_event`). `on_window_event(kind, f)` is the general form, with an `EventKind`, for the pointer events.

## What an event costs

Events are cheap by design, and a window doesn't render again for pointer events unless something is styled by them.

- **No render for hover, press or focus** unless the frame has something that depends on it: a `:hover`, `:active` or `:focus` rule in your CSS, a `.hover(..)` / `.active(..)` / `.focus(..)` style, a `whileHover` / `whileTap` / `whileFocus` gesture, or a link. Otherwise the listeners run and nothing is built again. With 3000 boxes, a pointer move is about 10 µs instead of about 9 ms.
- **A hit test skips what the pointer can't be in.** Each frame builds, on the first hit test, the end of every box's subtree and the rectangle holding it, so a pointer move doesn't visit every box.
- **A frame skips the kinds nothing listens to**, and window-wide listeners are kept in a list of their own, so they cost nothing to the elements that don't have one.
- **A move that ends over the same elements as the last one** stops after the hit test: no allocation, no events.

## The Window API

Every listener (and `render`) gets the `Window`. What it can do:

| Method | What it does |
| --- | --- |
| `viewport_size()`, `bounds()` | The content size, in logical pixels |
| `scale_factor()` | Device pixels per logical pixel |
| `mouse_position()` | The pointer, in logical pixels |
| `set_window_title(title)` | Change the title (a `<title>` element does it too) |
| `focus_id(id)`, `focused_id()` | Move or read keyboard focus |
| `is_hovered(id)` | Is the element with that `.id` under the pointer? |
| `scroll_offset(id)`, `set_scroll_offset(id, x, y)` | Read or set a scroll container's position |
| `refresh()` | Render again |
| `request_animation_frame()` | Render again on the next display refresh |
| `set_vsync(false)` | Let animation frames run as fast as the CPU allows (for benchmarks) |
| `is_gpu()` | Whether this window is drawing on the GPU right now |
| `is_animating()`, `needs_render()` | Whether CSS animations are running, or a render is pending |

### Animating from code

Call `window.request_animation_frame()` from `render` and the window renders again on the next display refresh. Frames are paced to the display; `set_vsync(false)` lifts the cap.

```rust
struct Spinner { angle: f32 }

impl Render for Spinner {
    fn render(&mut self, window: &mut Window, _: &mut Context<Self>) -> impl IntoElement {
        self.angle = (self.angle + 3.0) % 360.0;
        window.request_animation_frame();
        div().size(px(40.0)).bg(rgb(0x4772b3)).style(format!("rotate: {}deg", self.angle))
    }
}
```

For most motion, a CSS animation or transition is simpler and stops costing CPU when it's done: see [Effects and animations](../effects-and-animations/).

## Painting your own content

`canvas(|bounds, painter| ...)` is an element that paints itself with a `Painter`, in logical pixels, clipped to its box.

```rust
canvas(|b, p| {
    p.fill(b, rgb(0x232323));
    p.quad(b, 6.0, rgba(0x4772b380), rgb(0x4772b3), 1.0);       // rounded rect + border
    p.line(&[(b.origin.x, b.origin.y), (b.origin.x + 80.0, b.origin.y + 40.0)], white(), 2.0);
    p.oval(Bounds { origin: point(10.0, 10.0), size: size(20.0, 20.0) }, red(), black(), 1.0);
    p.text(b.origin.x + 4.0, b.origin.y + 4.0, "hello", 13.0, white());
})
.w(px(200.0)).h(px(100.0))
```

| `Painter` method | Draws |
| --- | --- |
| `fill(bounds, color)` | A filled rectangle |
| `quad(bounds, radius, fill, outline, width)` | A rounded rectangle with a border |
| `oval(bounds, fill, outline, width)` | An ellipse |
| `line(points, color, width)` | A polyline |
| `polygon(points, color)` | A filled polygon |
| `arc(bounds, start, extent, color)` | A pie slice |
| `text(x, y, text, size, color)` | A line of text |
| `image(bounds, image)` | An `Arc<Image>`, scaled to fit |
| `with_clip(bounds, f)` | Run `f` with drawing clipped to `bounds` |

A canvas is a normal element: size it, style it, give it listeners. For pictures from files, `img().src("file.png")` is simpler; see [Images](../html-elements/#images).
