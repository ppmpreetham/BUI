You already know how to build a UI: HTML for structure, CSS for looks, a little state to make it move. **The `blenderui` crate lets you do exactly that in Rust**, and draws the result with Blender's widget code in a native window. No browser, no webview, no JavaScript engine.

Write it in either of two first-class syntaxes: `rsx!`, HTML-like markup with components and hooks, or **gpui builders**, method chains like `div().flex().gap_2()` in the style of the [gpui](https://www.gpui.rs) crate. Style it with CSS, Tailwind classes or typed methods. Then decide, element by element, whether it should look like a web page or like Blender.

## What's in the crate

- **Every HTML element.** All 113 elements of the WHATWG index, from `div()` to `details()` and `dialog()`, plus `svg()` and `math()` as boxes.
- **Real CSS.** `<style>` sheets, selectors up to Level 4, the cascade, `var()`, `calc()`, flexbox, grid, tables, `@media`, `@container`, `@layer`, animations, transitions, filters and masks.
- **Tailwind CSS v4.** `class="md:hover:bg-sky-500/50"`, or bare attributes like `<div p-4 bg-[#4772b3]>`. A typo is a compile error that suggests the fix.
- **`rsx!` and hooks.** HTML-like markup, `#[component]` functions and hooks: `use_state`, `signal`, `Memo`, `Effect`, context.
- **gpui builders.** `Render`, `div().flex().gap_2()`, `cx.listener(...)`. The same gpui-syntax file compiles against blenderui and the gpui crate.
- **Blender's widgets.** `<NumberSlider>`, `<Button>`, `<ColorSwatch>` and friends are the real thing, with Blender's interaction rules and Blender's color picker.
- **Headless testing.** Render off-screen, click, type, scroll and step animations in a normal `cargo test`.

## Two ways to write the same thing

Here's one counter, two spellings. Both are complete, supported ways to write a BUI app: pick whichever reads better to you, and mix them in one app if you like. The tabs remember your choice across the Rust pages.

<Tabs sync="rust-syntax" label="Rust syntax">
<Tab label="rsx!">

```rust title="src/main.rs"
use blenderui::prelude::*;

#[component]
fn counter(label: &str) {
    let (count, set_count) = use_state(0);
    rsx! {
        <div flex items-center gap-3 p-4>
            <span>{label.to_string()} ": " {count().to_string()}</span>
            <button onClick={move || set_count(count() + 1)}>"Add one"</button>
        </div>
    }
}

struct Hello;

impl Render for Hello {
    fn render(&mut self, _: &mut Window, _: &mut Context<Self>) -> impl IntoElement {
        rsx! { <body styled><counter label="Clicks" /></body> }
    }
}

fn main() {
    Application::new().run(|cx| {
        cx.open_window(WindowOptions::default(), |_, cx| cx.new(|_| Hello)).unwrap();
    });
}
```

</Tab>
<Tab label="gpui builders">

```rust title="src/main.rs"
use blenderui::prelude::*;

struct Counter { count: i32 }

impl Render for Counter {
    fn render(&mut self, _window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement {
        div().styled().flex().flex_col().gap_2().p_4()
            .child(h1().child(format!("Count: {}", self.count)))
            .child(button().child("Add one").on_click(cx.listener(|this, _, _, cx| {
                this.count += 1;
                cx.notify();
            })))
    }
}

fn main() {
    Application::new().run(|cx: &mut App| {
        cx.open_window(WindowOptions::default(), |_, cx| cx.new(|_| Counter { count: 0 }))
            .unwrap();
    });
}
```

</Tab>
</Tabs>

- **`rsx!`** keeps state in hooks (`use_state`) inside `#[component]` functions, and listeners can leave out parameters they don't use.
- **gpui builders** keep state in the view's fields, and `cx.listener(...)` gives the closure `&mut` access to the view; `cx.notify()` renders again.

Both compile to the same calls: `rsx!` is lowered to builder methods at compile time, so there's no runtime parsing and no hidden cost. The [rsx! and components](../rsx-and-components/) page shows every markup rule, and [gpui syntax](../gpui-syntax/) covers the builder side and the app model.

## Three looks, one element type

Every element can look one of three ways, and you choose per subtree:

1. **Plain HTML** looks like a browser: black text on white, Chrome-style form controls.
2. **`styled`** gives an element and everything inside it Blender's theme (dark by default, or light with `blenderui::set_theme`) and Blender's widgets.
3. **Blender components** (`Button`, `NumberSlider` …) are always Blender's widgets, wherever you put them.

[The three looks](../styled-and-blender-components/) puts them side by side.

## Get it running

Add the crate from crates.io:

```sh
cargo add blenderui
```

The [installation page](../../start/installation/) has the details: you need Rust 1.88 or newer, CMake and a C compiler, because the first build compiles BUI's C kit. To build against another checkout of the C sources, set `BUI_SOURCE_DIR`.

The examples are the fastest way to see what's possible. From a clone of the repository:

```sh
cd bindings/rust
cargo run --release --example hello                 # an rsx! counter, with Tailwind and a slider
cargo run --example showcase                        # the window in the screenshot
cargo run --example showcase -- --screenshot a.png  # render it off-screen to a PNG
cargo run --example forms                           # the three looks side by side
cargo run --example counter                         # the gpui-syntax counter
cargo test                                          # unit, coverage and headless tests
```

## Rendering: CPU or GPU

Windows draw with BUI's software raster by default. It draws in parallel bands; `BUI_RASTER_THREADS=1` forces one thread. Ask for the GPU and you get the same pixels with the rasterizing off the CPU:

```rust
Application::new().gpu(true).run(|cx| { /* every window on the GPU */ });
// or one window:
cx.open_window(WindowOptions { gpu: Some(true), ..Default::default() }, build);
```

- The GPU renderer is **Direct3D 11 on Windows and OpenGL 3.3 on Linux**. Elsewhere, or without a device, windows stay on the software raster.
- `BUI_GPU=1` or `BUI_GPU=0` overrides both settings.
- `window.is_gpu()` turns `true` a few frames in, once the device is ready.
- Both renderers produce the same pixels; the `gpu_parity` test checks it.
- `BUI_PROFILE=1` prints per-phase frame times for either renderer.

Following Blender's instanced widget batches, every primitive becomes one instance of a single shader. Text runs and images are cached in atlases, and frames render into a persistent target, so only damaged regions redraw.

## Text and fonts

Text uses Blender's UI font, **Inter**, embedded in the library, so it looks the same on every platform. The default family (and `sans-serif`, `system-ui` or any unknown family) is Inter. Named families such as `"Segoe UI"` or `monospace` load from the platform's fonts. `BUI_FONT=path.ttf` replaces the default face, and you can register your own:

```rust
blenderui::add_font("Brand", false, false, include_bytes!("Brand-Regular.ttf"));
```

The two `bool`s say whether the face is bold and italic. It returns `false` if the bytes aren't a font.

On the GPU, glyphs are drawn straight from their outlines with Eric Lengyel's [Slug](https://github.com/EricLengyel/Slug) algorithm: one quad per glyph, exact coverage in the pixel shader, no glyph bitmaps. The alternative is a per-glyph bitmap atlas, as Blender does it: about half the GPU work, but bitmaps per size.

| | Slug (default) | Glyph atlas |
| --- | --- | --- |
| Build time | `slug` feature (default) | `default-features = false` |
| Run time | `Application::new().slug(true)` or `blenderui::set_slug(true)` | `.slug(false)` or `set_slug(false)` |
| Environment (overrides) | `BUI_SLUG=1` | `BUI_SLUG=0` |

The `gdi-text` feature draws text with Windows' GDI engine and system fonts instead.

## How it works

```text
 Render::render ─► element tree (one Div type for every tag)
        │
  cascade: UA sheet ▸ <style> sheets ▸ inline ▸ :hover/:active/:focus ▸ !important
        │          one handler table applies every property
  box tree: blocks, line boxes of words, flex/grid items, tables as flex
        │
  taffy layout ─► absolute boxes, clips, scroll offsets
        │
  paint ─► one display list on a kit canvas      form controls ─► kit widget nodes,
        │  (rects, rounded rects, text, images)                 placed at their boxes
        ▼
  C kit: input, hit testing, Blender widget drawing, damage rendering, native window
```

- **One implementation per property.** Every style source (methods, `css!`, `.css`, `.style`, sheets, the user-agent sheet, state refinements) becomes CSS declarations applied by one table of property handlers.
- **Work at compile time.** The property table is a `const`. Style methods and `css!` resolve property names when your program compiles, so a typo is a compile error, and fixed values like `.flex()` are tokenized once per program.
- **No `Rc` or `RefCell`.** A frame is a set of flat arenas linked by index, owned by the window and reused every frame. Entities are `Copy` handles into an app-owned slot map. The only shared ownership left is `Arc<Image>` for image pixels.
- **Reuse across frames.** `render()` builds a fresh element tree each frame, but the work behind it is reused: matched selectors are memoized, computed styles are shared, and the layout tree and widget nodes are reconciled by key, so only changed subtrees are laid out again.
- **`blenderui-sys`** is the raw FFI over the C kit's header (`kit/include/BUI_kit.h`). Its build script builds the kit with CMake and links it statically.

## Limitations at a glance

BUI's Rust side covers a lot, but not everything. Each page lists its own gaps; here they are in one place:

- **Text:** floats place block boxes, but text doesn't wrap around them. Right-to-left text is reordered but not shaped (no Arabic joining). There's no per-glyph fallback between the faces of a `font-family` list. `text-align: justify` aligns left.
- **Inline boxes** paint their background per word; borders and padding on inline elements (`<kbd>`, `<code>`) aren't drawn.
- **Widgets draw above page content**, so a `z-index`ed box such as a `<dialog>` over a form field doesn't cover the field.
- **Images**: every [format](/docs/concepts/images) decodes and animations play, but one inside a CSS effect layer (filters, masks, 3D transforms) shows its first frame. `video`, `audio` and `iframe` show a placeholder.
- **Transforms:** every 2D transform draws, but clicks use the untransformed box. 3D transforms have no effect.
- **Tables** size columns from their widest single-line content, a simpler version of browsers' auto layout.
- **Windows** are native on Windows (Win32), Linux (X11) and macOS (Cocoa). The Cocoa host is new and has been tried by hand on one Apple Silicon Mac so far, and it needs the main thread. The GPU renderer runs on Windows and Linux.
- **Components:** async resources (`use_resource`) and generic components are <ComingSoon inline />.
