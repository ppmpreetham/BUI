A table of a million rows is easy to ask for and hard to build: make one element per cell and the window stops responding. **`DataTable` draws only the cells you can see**, straight to the screen, the way Blender's spreadsheet editor does. Scrolling it costs about a millisecond, whether it holds a hundred rows or a million.

## A table in 30 lines

You describe your data with a **delegate** (what the columns are, and the text of any cell), keep the table's state in an entity, and put a `DataTable` in your view:

<Tabs sync="rust-syntax" label="Rust syntax">
<Tab label="rsx!">

```rust
use blenderui::prelude::*;
use blenderui::table::{Cell, CellSource, Column, DataTable, TableDelegate, TableState};

struct People;

// The cells: called for the cells in view only. Numbers are typed; the table
// formats them without allocating.
impl CellSource for People {
    fn cell(&self, row: usize, col: usize) -> Cell<'_> {
        Cell::U64(if col == 0 { row as u64 } else { row as u64 * 7 % 1000 })
    }
}

impl TableDelegate for People {
    fn columns_count(&self, _: &App) -> usize { 2 }
    fn rows_count(&self, _: &App) -> usize { 1_000_000 }
    fn column(&self, ix: usize, _: &App) -> Column {
        if ix == 0 { Column::new("id", "ID").sortable().width(px(80.0)).fixed_left() }
        else { Column::new("score", "Score").sortable() }
    }
}

struct App1 { table: Entity<TableState<People>> }

impl Render for App1 {
    fn render(&mut self, _: &mut Window, _: &mut Context<Self>) -> impl IntoElement {
        rsx! {
            <div class="w-full h-full">
                {DataTable::new(&self.table).stripe(true)}
            </div>
        }
    }
}
```

`Column` sets the width, whether it sorts, resizes, moves or is pinned, and how its text is aligned. A click on a sortable header sorts ascending, then descending, then back to the original order. Drag a header's right edge to resize it (double-click it to fit the content when your delegate implements `fit_column`), and drag a header sideways to move the column.

## Why it is fast

Blender's spreadsheet doesn't make a widget per cell. Each frame it works out which rows the scroll position shows (`first_row = scroll_y / row_height`, and `region_height / row_height + 1` of them), skips the columns that are off screen, and draws just those cells. BUI's table does the same:

- **Only visible cells are asked for.** `CellSource::cell` runs for the cells in view, never for the rest. The table has no per-row state, so building one costs nothing.
- **Cells are painted, not built.** There's no element, style or layout box per cell, so a frame builds the same handful of elements however many rows there are.
- **Sorting and filtering never copy rows.** They produce a list of row numbers (what Blender calls an index mask) and the table reads through it. A column of numbers or of text sorts through typed keys: one pass pulls an order-preserving integer out of each cell, then plain integer pairs are sorted on every core, with no call into your code per comparison.
- **A steady frame allocates nothing.** `cell` hands back a borrowed `&str` or a number that the table formats into a stack buffer, and the table's own drawing is covered by a test that counts allocations.
- **Nothing moves, nothing renders.** A table that isn't scrolling costs no CPU.

## One core, two frameworks

The table is split so that nothing is written twice. The `blenderui-table` crate has no dependencies and no framework: the visible-row math, column culling, the row index mask and the typed sorts, the selection model, keyboard navigation, column layout, Ctrl+C text, scrolling, hit testing, a bounded text-run cache, and the painting itself, which draws through a small `PaintSink` trait. A framework adapter adds three things and no logic: a `Host` that forwards your delegate's hooks and the redraw calls, a `PaintSink` that draws rectangles and text, and an element that hands pointer, wheel and key events to the core.

blenderui's own `table` module and the gpui adapter below are both such adapters, around the same `TableCore`.

## On gpui

`blenderui-table-gpui` is a `DataTable` for plain gpui with gpui-component's names (`TableDelegate`, `Column`, `ColumnSort`, `ColumnGroup`, `TableState`, `TableEvent`, `scroll_to_row`, `load_more` ...). It is a custom gpui `Element` that paints the visible cells with `Window::paint_quad` and shaped lines: two elements per frame, however many rows. It keeps shaped text in a cache keyed by text, color and size, so scrolling never reshapes a string it showed a frame ago.

```rust
use blenderui_table_gpui::*;

struct People;

impl CellSource for People {
    fn cell(&self, row: usize, col: usize) -> Cell<'_> {
        match col {
            0 => Cell::U64(row as u64),
            1 => Cell::Str(["Cube", "Sphere", "Torus"][row % 3]),
            _ => Cell::F64(row as f64 / 8.0, 2),
        }
    }
}

impl TableDelegate for People {
    fn columns_count(&self, _: &App) -> usize { 3 }
    fn rows_count(&self, _: &App) -> usize { 1_000_000 }
    fn column(&self, ix: usize, _: &App) -> Column {
        Column::new(format!("c{ix}"), ["ID", "Name", "Size"][ix]).sortable().width(px(110.0))
    }
}

// in render: div().size_full().child(DataTable::new(&self.table).stripe(true))
```

For a cell that needs real content, return `true` from `has_custom_cells` and `is_custom_cell(row, col)`, return `Cell::Empty` from `cell`, and build the element in `render_td`; only visible custom cells are built.

### Against gpui-component

Measured in a real window on the same gpui, with the same data, columns and row height, one process per library:

The frame time is the main thread's CPU time from render to the end of paint; it leaves out GPU work and the 60 Hz wait, which is why both show 60 FPS. The gaps are the point: about 3.3 times less time per scrolled frame, about 30 times fewer allocations, and a worse tail for the component (95th percentile 9 ms against 1.8 ms). ## What you get

| Feature | How |
| --- | --- |
| Sticky header, pinned columns, horizontal and vertical scrolling | built in; `Column::fixed_left()` pins a column |
| Column resize, move, sort | drag a header border, drag a header, click a header |
| Row selection | click; Ctrl-click toggles; Shift-click extends; Ctrl+A selects all |
| Cell and column selection | `cell_selectable(true)`, `col_selectable(true)` (one at a time) |
| Keyboard | Up, Down, Page Up, Page Down, Home, End; Left and Right in cell and column modes; Escape clears |
| Copy | Ctrl+C puts the selected rows on the clipboard as tab-separated text |
| Stripes, row-number column, borders | `stripe(true)`, `row_header(true)`, `bordered(true)` |
| Row sizes | `Size::XSmall` to `Size::Large`, from Blender's `UI_UNIT_Y` and the UI scale |
| Loading and empty states | `loading()` shows a skeleton; `empty_text()` |
| More rows when scrolled to the end | `has_more`, `load_more_threshold`, `load_more` |
| Filter | `TableState::set_filter(|data, row| ...)` |
| Themes | Blender's dark and light themes, with HiDPI |

Events come as `TableEvent` values, the same names gpui-component uses (`SelectRow`, `DoubleClickedRow`, `ColumnWidthsChanged`, `MoveColumn`, `RightClickedRow` ...). Listen with `on_event`, or with `on_select`, `on_sort`, `on_row_double_click`, `on_column_resize` and `on_context_menu`:

```rust
DataTable::new(&table)
    .stripe(true)
    .on_select(|row, _window, _cx| println!("row {row}"))
    .on_sort(|col, sort, _, _| println!("column {col}: {sort:?}"))
```

## Porting from gpui-component

The names follow gpui-component's `TableDelegate`, `Column`, `ColumnSort`, `ColumnGroup`, `TableState` and `DataTable`: `columns_count`, `rows_count`, `column`, `perform_sort`, `fit_column`, `move_column`, `group_headers`, `loading`, `has_more`, `load_more`, `visible_rows_changed`, `visible_columns_changed`, `selected_row`, `set_selected_row`, `visible_range`, `scroll_to_row`, `scroll_to_col`, `headers` and `dump`. Two things differ on purpose:

- **Cells are values drawn by the table.** gpui-component's `render_td` returns an element for every visible cell on every frame; here `cell` returns a typed value (`Cell::U64`, `Cell::Str`, `Cell::F64(value, decimals)`) and the table draws it, which is what makes a frame cost the same at any size. On gpui, `render_td` remains as an opt-in for the few cells that need real elements. In blenderui, cells that hold widgets aren't supported yet.
- **The table sorts for you.** The cells' own order sorts an index list (override `CellSource::sort_kind` and `compare` for a custom order); the delegate's data is never reordered. If you'd rather sort your own data in `perform_sort`, return `false` from `sort_by_mask`.

Row numbers in events and in `selected_row` are your delegate's row numbers, so they stay right when the table is sorted or filtered.

## Long lists: `uniform_list`

For a list of equal-height items that are real elements (buttons, icons, rows with their own widgets), `uniform_list` takes gpui's signature and builds only the items in view:

```rust
uniform_list("files", 100_000, |range, _window, _cx| {
    range.map(|i| div().child(format!("File {i}"))).collect::<Vec<_>>()
})
.item_height(px(20.0))
.h(px(300.0))
```

It uses the same visible-range code as the table. The scroll offset is kept per id like any scrolling element, and the scrollbar is sized for all the items. Layout works in `f32`, so past about 16 million pixels of total height (a million 24 px rows) the position loses sub-pixel precision; the `DataTable` keeps its own offset in `f64` and has no such limit.

## Testing a table

Tables run off-screen like everything else, so your tests can click headers, drag borders and press keys. `tests/table.rs` does exactly that, on a million-row table; see [headless testing](../headless-testing/).

## Limitations

- **No element cells in blenderui yet** (the gpui adapter has the `render_td` escape hatch), and no popup context menu: right clicks arrive as `TableEvent::RightClickedRow`.
- **Selection after a sort or filter is cleared**, because selected rows are display positions.
- **Cell and column selection hold one cell or column**, not a range. Row selection takes ranges.
- **Column groups** (`group_headers`) draw, but aren't covered by a test yet.
- **JavaScript and Python wrappers: coming soon.** The table is built once, in Rust; the other languages will wrap it rather than reimplement it.
- **Damage rectangles inside the table aren't reported.** A scroll or hover redraws the table's canvas as a whole; the engine's damage rendering for the rest of the window is unchanged.
